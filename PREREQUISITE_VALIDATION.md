## EPERM investigation

Execution host: Windows (`process.platform === 'win32'`), Node v24.15.0, npm 11.12.1. macOS filesystem/privacy controls do not apply.

Working/project directory: `C:\Users\Administrator\Self Study\SIASET`. There is no `.git` repository; `git rev-parse --show-toplevel` reports that this is not a Git repository. The folder is the local project root, not a verified Git checkout.

Inspected the project, `frontend`, `frontend/src`, `frontend/src/main.jsx`, and ancestor directory attributes. They are ordinary directories/files without symlink targets or reparse/synchronization attributes. The project path is outside OneDrive. Ownership is `BUILTIN\Administrators`; ACLs include read/execute for `CodexSandboxUsers` and full control for the named local user, Administrators and SYSTEM. No ACLs or ownership were changed.

Direct Node reproduction, independent of Vite:

| Operation | Result |
| --- | --- |
| `fs.statSync` / `fs.lstatSync` | Succeed; main.jsx is a regular file, not a symlink |
| `fs.readFileSync(main.jsx)` | Succeeds, 2161 bytes at inspection |
| `fs.realpathSync(main.jsx)` | Succeeds with the expected absolute path |
| `fs.realpathSync.native(main.jsx)` | Fails `EPERM` |
| Native realpath on project root, source directory and React package.json | Fails `EPERM` |
| Native realpath on ancestor paths and executor TEMP directory | Also fails `EPERM` |

The observed cause is native Windows path canonicalization failing in the restricted execution context, rather than a denied source read or a React syntax defect. The precise underlying Windows sandbox policy/hook is not independently identifiable from these observations; it is not attributed to an arbitrary Vite bug or to an invented ownership problem.

Vite 7.3.7's installed resolver calls `safeRealpathSync` when `preserveSymlinks` is false. Setting `resolve.preserveSymlinks: true` avoids that native canonicalization step and makes the actual build pass. This preserves logical module paths; it does not alter permissions or disable security. Since this project has no linked workspace packages/symlinks, no such package-identity change is currently expected. Reassess the setting if symlinked dependencies are introduced. The environment's native-realpath restriction itself remains; the application build no longer depends on the failing call.
